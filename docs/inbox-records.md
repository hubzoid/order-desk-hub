# Inbox records and reports

New inbox setup explicitly writes `DESK_ERP_ENABLED: false`. Existing connector-based installations without that setting retain ERP behavior; the shipped settings do not turn their addon off. Extraction and verification produce versioned normalized records without ERP configuration or master lookup. Every record retains original extraction, source elements, source event, rule digest and reviewer. Human corrections create a revision and never replace the original extraction. Replaying the same intake event returns its existing case. A forwarded document with the same scoped party/reference becomes a duplicate candidate and is excluded from accepted totals. Distinct events remain inspectable. Separate accounts/companies have separate receipt and data access boundaries.

Use `desk_case` to see source lines, exceptions, current record revision and available actions. `desk_review_record` corrects fields and can accept only a validated record. Human review does not approve ERP posting. Quantity, unit, rate, date, currency, tax, stated total and party/reference must be supported. A tax basis can be confirmed as an explicit case correction. Source verification problems or multiple attachments require explicit source acknowledgements, with the originals retained. Unsupported credits/cancellations are exceptions. Dismiss a confirmed duplicate with cancel; this writes an immutable superseded revision and clears it from exception aging. Duplicate candidates remain excluded until reviewed, never guessed away.

The four reports are `register`, `orders`, `invoices`, `exceptions`. Only register has a CSV export. Safe CSV prefixes formula-leading cells and preserves original strings in the stored record. Financial reports include the current latest revision only when accepted. A later unresolved correction excludes that document until accepted again, rather than falling back to a known stale accepted amount. Unknown amount/currency/date, unreviewed, superseded, conflicting and duplicate records are excluded explicitly. Report metadata shows filters, generation time and included revisions. No FX conversion. Source units remain separate. Approved conversions appear separately without rewriting source quantities. Dates use inclusive start and exclusive end. A source date-only value is never timezone-shifted. Timestamp filters use the requested timezone. Undated exceptions stay visible. Age is elapsed seconds from exception creation to report generation.

Money uses Decimal. The default requires exact header/line/tax reconciliation at stated precision, with no implied rounding. A typed reviewed tolerance or half-up rule can allow the company's documented alternative. Tax-inclusive/exclusive treatment must be in evidence, reviewed company rules or an explicit human correction. Neither confidence nor prose policy silently decides it. An invoice is not proof of payment. An order is not proof of stock or fulfilment.

`knowledge/record-rules.md` has standard name/description frontmatter with typed values nested under `rules`. Legacy `knowledge/record-rules.yaml` remains readable only when no Markdown rule file exists. New reviewed changes create or edit the Markdown authority and preserve legacy source bytes. The typed rules accept only version, company, auto_accept, tolerance, rounding, default_tax_basis, exact aliases, sourced item/unit conversions and source_refs. Alias conflicts fail validation. Source paths must remain inside the Hub, including symlinks. Keep automatic acceptance off until the owner reviews the rules and holdout outputs. New ambiguity stays a question. ERP aliases/policies remain separate and keep their existing contracts.

Access uses `desk_view`/`desk_operate` plus the source grant returned by setup, bound to channel and mailbox account. Uploads remain visible to their authenticated uploader or explicitly granted upload source scope. Changing a connected account does not reuse the old account scope. Direct tools and reports recheck grants. Local CLI access assumes trusted host ownership, not arbitrary API caller authority. Shared context and action policies are file-held. SDK identities, membership, credentials and approvals retain their SDK authority. On writable source, chat/MCP correction proposals use SDK change storage and an authorized human activates them. On read-only source the tool returns a readable diff for authorized builder checkout review/redeploy, and creates no pending proposal. After a rule activation, existing cases expose rerun; saved source acknowledgements and case corrections survive it.

The same domain services and rule/evidence revisions power chat, workflows, CLI and MCP. Raw MCP clients own their final phrasing. Only delegated hub-agent execution applies this Hub's prompt. Live source evidence is recorded rather than claimed repeatable.

Historical import and recurring polling have separate scopes. The historical query/date range does not filter future Gmail polling. Recurring polling uses configured Gmail label IDs. Choose a dedicated business mailbox or existing business labels, or explicitly review whole-INBOX retention. Setup previews the actual ongoing mailbox/labels and preserves existing channel settings. No new Gmail label or provider UI step is required. Tokens are saved automatically by OAuth in a distinct channel-scoped SDK slot.
