# Qualification, limits and recovery

This build has no live mailbox/model/ERP/hosted qualification claim. Model-free tests and stand-ins are labelled synthetic. The required real matrix in proposals remains outstanding: local Claude through Claude Code and Cowork separately, local Codex through Codex authoring, Railway Claude/Codex, and Maritime Claude/Codex with the specified authoring surfaces. No paid resources or customer mailbox/ERP writes are authorized by this build. Every promoted combination needs real Gmail records and all four outputs, teammate scope, restart, schedules, callback, sleep/wake, backup/restore and upgrade evidence. ERPNext draft/approval/submission/recovery needs its own real evidence on every advertised host/runtime row. A skipped credential/provider check is a gap, never a pass.

The bounded history command needs Hubzoid 2.0.1 or later. hub.lock.json records that range, and doctor checks the installed release against it. When a lock names an exact commit instead, doctor checks non-editable VCS installs through PEP 610 commit metadata and editable checkouts through their own Git root. An unverifiable or mismatched locked revision fails. Do not install a moving branch and treat its version number as evidence.

The current Gmail connection requires customer-owned OAuth, external consent and selected sender admission. A business label is preferred but optional. A bounded reviewed business query is supported. All selected source material is retained. Automatic unrelated-mail purging is deferred because SDK intake persists evidence before classification and exposes no safe discard API. Never advertise broad personal-inbox auto-import or unrelated-body deletion. Retention must be explicitly selected and documented by the operator.

Trusted host authoring and existing authenticated human approval cards are the concrete setup/action path. A generic delegated setup identity that cannot exercise an administrator's authority is deferred SDK hardening, not a property claimed here. Do not present CLI invocation as protection from a hostile machine owner. Cowork uses an existing supported bridge only and must report missing terminal/auth capabilities.

A message with multiple business documents/attachments is conservatively excepted for source review instead of silently combining accepted totals. Split the documents into separate uploads when needed, retaining source references. Parsing limits and accepted document types remain in the existing operator guide. Unsupported tax/rounding, credits and amended documents remain exceptions until a scoped supported rule exists.

Before upgrade pause intake and ERP writes. Back up the SDK data root and the approved Hub source revision together. The normalized-record table is additive and preserves existing case/proposal/evidence/ERP link tables. Existing installations with an explicit ERP connector but no DESK_ERP_ENABLED setting retain the old path. New inbox setup explicitly sets false. Never bulk rerun accepted work or re-post linked records during upgrade. Restore the compatible source/data pair, preserve intake receipts and operation references, and reconcile uncertain ERP operations before resuming. A backup cannot undo a submitted ERP transaction.

Draft receipt checking uses a durable business fence per ERP site/company, committed before HTTP and retained across crashes or uncertain writes. It has no expiry. A different invoice is blocked before dispatch even if the original case has not yet synchronized its SDK sending/ambiguous state. The same exact logical operation follows existing SDK recovery. Only a fresh claim with a definitive never-dispatched or definitively rejected/unsaved result can be released without readback. Otherwise release requires the exact named readback and a durable recorded draft. An absent read, cancellation or abandon does not release a possibly delayed write. Health and reconciliation show the held original operation. Independent hubs or non-Hubzoid ERP writers are not protected by this local lock and require ERP-side validation. A lost invoice-write outcome blocks competing receipt allocation until reconciled. Every submission still requires exact human approval and an ERP version/digest check. Changed rule revisions stop dispatch for a fresh review. Submitted content changes stay in the open needs_review state, with docstatus 1 and a clear human review instruction. They retain the ERP's actual totals rather than presenting stale proposal totals.

Historical import and recurring polling have separate scopes. The historical query/date range does not filter future Gmail polling. Recurring polling uses configured Gmail label IDs. Choose a dedicated business mailbox or existing business labels, or explicitly review whole-INBOX retention. Setup previews the actual ongoing mailbox/labels and preserves existing channel settings. No new Gmail label or provider UI step is required. Tokens are saved automatically by OAuth in a distinct channel-scoped SDK slot.

Upgrade checks fail closed when legacy `<hub>/.hubzoid/data/desk` or `erp` exists while the configured SDK data root differs. No new ERP deployment identity is generated. With every hub/poller/worker stopped, review a backup of source and all operational data, then move the existing `desk` and `erp` directories into the configured root's `.hubzoid/data/`, preserving the ERP `deployment-id`, SQLite databases/WAL files, source evidence, SDK operation receipts and keys. Do not merge competing stores or leave an active legacy copy. Keep the backup outside either active state path. Verify case/proposal/link counts and the unchanged deployment identity, reconcile uncertain operations, run doctor, then resume. If both roots already contain state, stop and review which authoritative source/data pair to restore. Never regenerate identity or bulk repost. An addon-off setting with existing ERP cases/pending links also fails doctor: keep the ERP path until an explicit conversion is reviewed.

Hosted access administrators now need explicit desk and source grants; `manage_access` alone no longer grants business-data access. Before resuming, an authorized administrator runs `hubzoid grant MEMBER_EMAIL desk_view .`, `hubzoid grant MEMBER_EMAIL desk_operate .`, the required workflow grant, and `hubzoid grant MEMBER_EMAIL SOURCE_GRANT .` using setup's exact source grant. Add desk_manage/desk_submit only for those roles. Re-test a scoped teammate; no automatic grant widening occurs.

Setup requires one existing business label or explicit `--whole-inbox` consent. Its digest binds the actual ongoing mailbox/label retention scope. This does not imply the historical keyword query filters new mail. Multiple labels remain unsupported in this hub until poll/import semantics agree.

Deferred optional review notes: needs_review stays open for ERP-side investigation, without a new acknowledgement platform; original ERP source records require separate review before record reports count them. The durable fence covers one site/company rather than individual receipt rows. Source line reconciliation remains exact; half-up/tolerance controls header reconciliation only. No new import purge, generic ETL engine or automatic prose execution was added.
